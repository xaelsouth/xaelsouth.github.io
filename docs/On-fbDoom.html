On fbDOOM

Estimated reading time: 5 minutes · Page generated: 2026-11-07T20:58:28+00:00

fbDOOM is an adaptation of the original DOOM engine for devices where a conventional desktop graphics stack may not be available. Instead of depending on SDL or OpenGL, its Linux build can render directly to the framebuffer and read input from Linux event devices. There is also an X11 software backend for desktop testing.

The project is especially interesting as a way to bring a familiar game to small and unusual displays. Its README lists plain Linux framebuffer systems, a Siglent SSA 3021X Spectrum Analyzer, Frosted OS, Kinco Green Series GL070HE and MT4434TE HMIs, and NXP i.MX23 boards among its targets.

Where it comes from

This is a fork of maximevince/fbDOOM, Maxime Vince's framebuffer port, which in turn builds on the original id Software DOOM source release. The fork keeps the minimal-dependency approach and extends it with the i.MX23 PXP/DRM video path, OPL music emulation for CPUs without an FPU, and the optional rendering features described below. The music code comes from Chocolate Doom.

[!NOTE] The changes in this fork were made exclusively by AI. I don't claim any credit for that work. Credit for the underlying code belongs to id Software, Chocolate Doom, and the upstream fbDOOM authors.

Building and running

For a native Linux framebuffer build, install a C compiler and run:

cd fbdoom
make

The Makefile detects optional dependencies. If ALSA development headers are available, the build includes music and sound effects; without them, it still builds without sound. To build the desktop X11 test version, install the Xlib development files and use:

cd fbdoom
make BACKEND=x11
./fbdoom-x11 -scale 3

Here -scale 3 sets the window size to three times the base 320×240 picture (960×720). It accepts integer values from 1 to 8, and -fullscreen ignores it.

For a cross-build, the README gives this example:

cd fbdoom
make CROSS_COMPILE=arm-linux-gnueabihf-

On framebuffer displays, use -stretch to fill the screen instead of preserving the aspect ratio, or -scaling N to choose a smaller integer-scaled viewport. The X11 version supports window scaling and fullscreen mode. The framebuffer build needs access to /dev/fb0 and a keyboard device under /dev/input/event*; a mouse is optional. Device permissions therefore need to be set up for the user running the game.

As in other DOOM source ports, the engine needs a game data file (an IWAD) to play. The original DOOM shareware IWAD is still available online from various archives; use a legitimate copy and check the source and terms before downloading. The usual options are supported, including -iwad, -file for add-on PWADs, -skill, -warp, and -playdemo. W/S move forward and backward, A/D strafe, and the arrow keys turn by default.

High-resolution rendering

By default, the game renders internally at 320×200 and fits the picture to the display while preserving its aspect ratio. Pass -hires (or -res 640x400) to render at 640×400 for finer geometry; textures and sprites are still scaled up, and the higher resolution requires about four times the pixel work. On the i.MX23, performance can reach up to 50 FPS at 320×240 output, and about 20 FPS with hires enabled. Actual frame rates depend on the scene and configuration. The -scale option keeps the same window size at either resolution.

Making use of the i.MX23 PXP

The i.MX23 has a Pixel Pipeline (PXP) that can do the final image scaling and colour conversion in hardware. Build with PXP support when the target headers are available, then run the framebuffer executable with -pxp. fbDOOM converts the game’s indexed-colour frame to YUV and lets the PXP produce the display-sized image. If the hardware path is unavailable at runtime, it reports that and falls back to CPU scaling.

When DRM and a suitable framebuffer are available, the PXP output can be sent directly to a DRM scanout buffer, avoiding an extra frame copy. Otherwise the result is copied to the framebuffer. Use -pxpfb to force that copy path, or -pxpdev /dev/videoN to select a PXP V4L2 device explicitly. This acceleration is specific to the fbdev backend and is optional; the ordinary software renderer remains the default.

Sound

Music is generated with an emulated OPL2 (AdLib) chip and mixed with sound effects through ALSA; it does not require MIDI hardware. -nomusic and -nosfx disable either component, while -nosound disables audio initialization altogether.

Rendering options

Optional visual features include -flashlight, -brightmaps, and -translucent; these are off by default. -showfps displays a frame-rate counter.

Vertical view (freelook)

Original DOOM has no way to look up or down. fbDOOM adds an optional vertical view, enabled with -freelook. Mouse up/down, PgUp/PgDn and End (to re-center) tilt the view as a horizon shift rather than true 3D pitch, which keeps it cheap for the software renderer. It affects local view state only, so demos and netgames are unaffected. Without -freelook, the mouse moves the player forward and back as in classic DOOM. Add -invertlook, or set mouse_invert_look 1 in default.cfg, to invert the vertical mouse axis.
