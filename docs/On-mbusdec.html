On mbusdec and rtl-wmbus

rtl-wmbus receives Wireless M-Bus signals from an SDR and turns them into telegrams. What if you want to inspect the meter data inside those telegrams? mbusdec is a C library and command-line decoder that can read the receiver's output and produce newline-delimited JSON.

The two programs do different jobs. rtl-wmbus demodulates the radio signal, checks the received packet and removes link-layer CRC bytes. mbusdec parses the resulting telegram, identifies the meter, and decodes supported application records. The library also supports wired M-Bus long frames, though the CLI currently accepts only the rtl-wmbus stream format.

[!NOTE] mbusdec was written and tested by AI as an experiment using the EN 13757 and OMS specifications and publicly available test vectors, including wmbusmeters examples. It implements a subset of the standards and is not certified. Check the project README for supported formats and limitations.

Building

The following assumes that both repositories have been checked out side by side, and that rtl-wmbus's RTL-SDR dependencies are installed:

# Go into rtl-wmbus folder
cd rtl-wmbus
make release

# Go into mbusdec folder
cd mbusdec
cmake -S . -B build
cmake --build build

mbusdec needs CMake, a C11 compiler and the math library. Its default AES backend is bundled; OpenSSL is an optional alternative. See the project README for build options, tests and platform-specific instructions.

Decoding a recording

From the parent directory of the two checkouts, try the included I/Q sample:

./rtl-wmbus/build/rtl_wmbus \
  < ./rtl-wmbus/samples/rtlsdr_868.950M_1M6_samples2.cu8 \
  | ./mbusdec/build/mbusdec

Pipe mbusdec into jq for well-formatted JSON document.

Each output line is a JSON object, either a decoded telegram or an error. For example, a decoded telegram contains identities and records where these are available. decode_status describes the decoder outcome; it is distinct from the meter's transport status. Receiver RSSI values are included when available, but are not calibrated dBm measurements.

Not every reception necessarily decodes: this sample can also produce a receiver-reported CRC failure or an unsupported telegram. mbusdec reports these as JSON errors, continues processing subsequent lines, and exits nonzero at end of input if any line failed. It trusts rtl-wmbus's CRC status because the CRC bytes have already been removed.

For a live T1/C1 receiver, the same decoder can follow rtl_sdr and rtl-wmbus:

rtl_sdr -f 868.95M -s 1600000 - 2>/dev/null \
  | ./rtl-wmbus/build/rtl_wmbus \
  | ./mbusdec/build/mbusdec

The rtl-wmbus README describes other modes, frequency settings and receiver options. Receive and decode only telegrams you are authorized to access, and protect any meter data you collect.

Keys and address filters

Some meters encrypt their application data. Supply the appropriate meter keys in a JSON file with --keys:

rtl_sdr -f 868.95M -s 1600000 - 2>/dev/null \
  | ./rtl-wmbus/build/rtl_wmbus \
  | ./mbusdec/build/mbusdec --keys keys.json --filter filter.json

Both files are read at startup. The example key file shows the address and key format; its keys are public test values, not keys for your meters. Keep real keys private. The example filter uses the same address fields but does not need keys.

A filter entry can identify an application-layer address, optionally constrained by a link-layer address, or just a link-layer address. Any matching entry lets a telegram through; an empty array ([]) allows all telegrams. Nonmatching telegrams are silently skipped before decryption. Omit --filter to process all telegrams, and omit --keys when keys are not needed. Malformed input, CRC failures and headers that cannot be inspected are still reported as errors. Filter addresses in the example are illustrative: replace them with the identities of the meters you want to monitor.

Using the library

mbusdec can also be linked into a C application without the CLI. The build produces libmbus.a and the public interface is in mbus.h. The library accepts wired long frames and CRC-stripped wireless telegrams, supports selected encrypted transport modes, and lets applications register manufacturer-specific decoders. See the library documentation and examples for the API, supported records and limitations.
