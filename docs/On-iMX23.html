On iMX23

Estimated reading time: 25 minutes · Page generated: 2026-11-10T11:10:31+00:00

Why bother with such rusty stuff at all? Just for fun. Kind of attached to fixing broken or incomplete things. Perhaps two and a half people might find this helpful too.

Hardware and tested configuration

Recently, whilst tidying up my stuff after moving into a new house, I found two boards: the Olinuxino Mini and the iMX233 EVK. Both are built around the iMX233 SoC, originally from Freescale, which later became part of NXP. The SoC has been officially obsolete for many years.

[!TIP] For less patient readers: here is my Buildroot for imx23 branch, which includes all the patches I made in an attempt to provide better support for the iMX23 platform. I hope it might be interesting to someone considering options to upgrade a fleet of iMX23-based devices.

The experiments below use the Buildroot branch above; the captured EVK logs show Linux 6.6.143 and U-Boot 2024.04. Here is a quick summary; the Olinuxino results are from the initial SD-card boot, before the later driver work. The patches originally developed for U-Boot 2024.04 were subsequently forward-ported to U-Boot 2027.01-rc1 in the i.MX23 U-Boot branch.

The details below distinguish initial findings from later results with patches.

Olinuxino Mini

According to the schematics, the Olinuxino Mini does not exactly have a lot of hardware to test after booting from a microSD card. My initial results were:

  • works: microSD card (via SPI), USB host, RTC with watchdog, GPIO
  • does not work: line in, line out, composite video/TV-out
  • untested: JTAG, PWM, I2C, DCP (crypto hardware), LRADC (analog to digital converter)

iMX233 EVK

In terms of hardware, the iMX233 EVK is much more interesting; just look at the schematics (SPF_77066.pdf)! The board is fitted with 8-bit NAND, UART, ENC28J60 SPI Ethernet, SD card slot, an array of buttons, an LCD, I2C devices (ADC, accelerometer, 24LC128 EEPROM) and two PWM-controlled LEDs. 128MB(!) RAM is quite cool too! Maybe I could run some sort of web kiosk thing with that board... 😋, but back to reality.

After booting from SD card, the LCD lights up immediately, which means that the LCD and the PWM used for its backlight work. Check.

Sad, but SPI Ethernet is multiplexed with the SD card interface and can work only if booted from USB or NAND.

The application UART works, so at least we could use SLIP at no less than 115200 bps or approx. 10KB/s 😒. Anyway, check.

While trying to test the accelerometer and EEPROM on the I2C bus, I quickly realised that constantly plugging and unplugging SD card during development really sucks. So I considered ordering a USB-SD-Mux FAST. Even its price, approx. 120€, didn't put me off, but I would have to wait for several days, or maybe even weeks, until the package arrived from Europe! Anyway, right after spending 120€ I came up with the idea of trying USB boot. Unfortunately, due to the old hardware and not very well maintained drivers and tools, I ran into a whole bunch of bugs and issues. Below I am going to describe how I tackled them.

Getting started: Buildroot and SD boot

An initial search on the internet brought me to the OpenWRT iMX233 Olinuxino page. The first impression was less than great. I would have expected a mature SoC platform, but looking at what is under 'Working', it appears that almost only USB works?.. Considering 'last worked with 3.18, driver needs to be fwdported' - everything else might or might not work. To jump ahead: I just wanted to play a bit with the very cool DirectFB2 project and the LCD attached to the iMX233 EVK to see what DirectFB2 could be useful for, but... Well, it's open source, so ~~save~~ help yourselves!

The next stop for board support was Buildroot. Luckily enough, Buildroot includes configuration files for both boards. Having enough experience with Buildroot, I forked it at https://github.com/xaelsouth/buildroot/tree/feature/imx23, cloned it and then kicked off the builds from the Buildroot checkout:

(make O=output/imx233_olinuxino olimex_imx233_olinuxino_defconfig && cd output/imx233_olinuxino && make -j$(nproc))
(make O=output/imx233_evk imx23evk_defconfig && cd output/imx233_evk && make -j$(nproc))

Waiting ⌛ ☕ ⌛ ☕ ⌛ ...

A few coffee cups later I was presented with an sdcard.img - one for each board - ready to write to SD card. The iMX233 readme and Olinuxino readme explain that better than I ever could. The Olinuxino uses a microSD card, whereas the iMX233 EVK wants a full-size SD card.

Booting via USB

According to the Linux BSP guide, the iMX23 ROM loads a so-called bootstream from the boot media configured by DIP switches or OTP fuses. It uses this to initialise the hardware and finally boot Linux. A bootstream is usually split into multiple bootlets: one initialises the power supply, the next initialises clocks and RAM, and a third optionally creates ATAGS for the Linux kernel command line. Even the Linux kernel can be considered a bootlet. Since a picture is worth a thousand words, here it is, borrowed from i.MX23 Linux BSP User Guide:

Bootlets can be found in the Buildroot tree at boot/mxs-bootlets. When using mxs-bootlets, the boot sequence is as follows:

  1. power_prep for power supply initialisation
  2. boot_prep for clock and RAM initialisation
  3. Optional Boot (proper), which can load a device tree, an initial ramdisk if applicable, and the Linux kernel from boot media
  4. The Linux kernel with an initial ramdisk and a device tree. Its command line may be populated by U-Boot, specified as bootargs in the device tree, or compiled into the kernel statically.

[!NOTE] Using mxs-bootlets makes sense if long-proven bootlets for power and RAM initialisation have to be preserved.

Although mxs-bootlets work with the iMX233 EVK board, using them does not make much sense here since U-Boot replaces the bootlets with its own implementation. In that case, the bootstream includes exactly two bootlets. For example, when booting from SD card:

  1. U-Boot SPL for power and RAM initialisation
  2. U-Boot (proper) to boot Linux

Now enough about bootstreams and their alternatives. How to use them for USB boot?

Windows users might consider sb_loader. I don't know how or whether it works, sorry.

Lucky Linux users like me can use sb_loader, which is compiled as a host utility. While creating the imx-sb-loader package, I took the liberty of including the source file in the package. BTW, sbloader.c was developed in 2010, 16 years ago at the time of writing, and still works - very impressive!

With sb_loader ready, I was still missing the bootstream (that vulgar file with an .sb extension) from the build artefacts folder, usually output/images. Turns out, BR2_TARGET_UBOOT_FORMAT_SB must be enabled for u-boot.sb to be copied along with the other binaries. With the DIP switch set to 0000 and the debug serial port (115200 8N1) connected using a USB-to-RS232 serial cable, let's boot u-boot.sb:

# Host PC
sudo output/imx233_evk/host/bin/sb_loader -d -p hid output/imx233_evk/images/u-boot.sb

BootROM loads and calls U-Boot SPL, which gets stuck there for an unknown reason, whilst the same code works when booting from SD card 😕. Nah, at least something works! (Reading this, one might recognise how low my expectations of finding something working already are.)

The disadvantage of the patch mentioned above is that the correct RAM size must be hard-coded as PHYS_SDRAM_1_SIZE.

The boot command would now boot Linux from SD card, which is not exactly what I wanted, since Ethernet would still be blocked by the SD card. Also, at this point I couldn't use NAND to load the Linux kernel because the MXS NAND driver for iMX23 was sort of unsupported. Bump.

Another bump came when I wanted to enable the ENC28J60 driver in U-Boot. I remembered U-Boot having this driver (yes, I'm that old), but it had been removed a long time ago due to its incompatibility with device tree and poor quality. And I did not want to bring it back. Maybe later. Maybe. Later. Means never.

[!NOTE] Update from "never" on 2026-Nov-08: I added both USB gadget networking and SPI Ethernet support to the i.MX23 U-Boot branch.

The solution to 'where-to-get-the-Linux-kernel-to-load' problem was to create a bootstream with a preloaded ITB file containing Linux, an initial ramdisk and a device tree. I used the following bootstream template, the elftosb tool and a post-build.sh script to replace %WHATEVER% with the full paths of the associated files:

options {
    driveTag = 0x00;
    flags = 0x01;
}

sources {
    u_boot_spl="%UBOOT_SPL%";
    u_boot="%UBOOT_BIN%";
    itb_image="%ITB_IMAGE%";
}

section (0) {
    load u_boot_spl > 0x1000;
    call 0x1000;

    // Load ITB image 0x46000000
    load itb_image > 0x46000000;

    load u_boot  > 0x40002000;
    jump 0x40002000;
}

[!NOTE] The elftosb package had to be activated as a host package. I don't know why, but despite being among the packages it was not included in package/Config.host.in.

Booting via NAND

The following EVK experiment builds on the USB boot above and uses the patched kobs-ng, together with the NAND and DCP driver work described in Hardware and driver findings. Keep a working USB recovery path before changing NAND.

There are two thoughts I would eagerly like to share about using NAND in embedded devices:

  1. Using raw NAND must definitely be banned from the embedded world.
  2. Using raw NAND might be allowed only in very low-cost consumer devices whose lifetime is often limited to a couple of years.

When using NAND in their devices, developers are required to maintain ALL related tools specific to their chosen SoC for years, even after the SoC platform has become officially obsolete! Industrial-grade devices are often developed for a service period of ten years, which, at the suggestion of marketing and other very important departments, will be prolonged by another ten almost always.

NAND tools must be SoC-specific because each SoC integrates its own NAND Flash Controller (NFC), e.g. the GPMI NAND controller for the iMX series. These controllers determine how data is physically accessed and protected with error correction codes, making generic tools incompatible across different hardware platforms.

What else adds to the complexity?

  • proprietary hardware interfaces: every SoC manufacturer designs their NFC differently. Tools must utilize hardware-specific commands to communicate with the chip.
  • vendor-specific ECC: raw NAND flash requires error correction code (ECC) to prevent data corruption. Because different SoCs use different ECC algorithms, the tools must encode/decode data exactly as the target SoC expects it.
  • bad block management (BBM): SoCs employ proprietary software or hardware schemes to map around physically defective memory blocks. Generic tools cannot inherently parse these custom bad block tables.
  • BootROM & security protocols: SoCs use secure boot chains with custom encryption keys, headers, and authentication methods. Tools must package firmware images precisely according to these SoC-enforced constraints => iMX23 bootstream.
  • flashing & recovery mechanisms: recovery modes for unbootable boards rely on SoC-specific ROM codes. Tools use these vendor-developed USB/UART protocols to bypass broken operating systems and push fresh bootloaders.

That's probably why all sensible developers would rather use eMMC with standard tools! (In the meantime, I'm gonna get a t-shirt with the quote "I love eMMC!" on it.)

kobs-ng

When configured to boot from NAND (DIP switch 0100), the iMX23 searches for a bootstream in a specific format, written to NAND flash using a specific pattern. This pattern is intended to let the SoC boot even if a copy of the bootstream is affected by a bad block.

kobs-ng is the tool of choice when a bootstream must be written to NAND. The only thing is - it did not work with iMX23 and the 6.6.y Linux kernel.

Long story short: I used the NAND simulator to debug kobs-ng and craft a patch. The patch can be found here https://github.com/xaelsouth/buildroot/blob/feature/imx23/board/freescale/common/patches/imx-kobs/0001-added-support-for-imx23-and-dcp.patch. What does it include?

  • iMX23/iMX28 SoC detection
  • bugfixes
  • removed annoying warnings
  • DCP crypto hardware can be used to program devices with crypto keys set

2k vs. 4k NAND page size

Using nandsim to get kobs-ng working was helpful, but the ultimate proof that iMX23 can boot from NAND is, obviously, iMX23 booting from NAND. And, as always, it did not work with the iMX23 EVK at first. BootROM was showing 0x80508003 (Unable to find LDLB), see iMX23 ROM error codes. At least it could find the NCB.

While kobs-ng did not work with the iMX23 EVK, it did work fine when programming a custom board with NAND page size = 2k and erase block size = 128k. To recap, the iMX23 EVK has Samsung NAND flash with page size = 4k and erase block size = 512k.

After trying multiple weird things and reading the reference manual for another three half-days, I finally found the answer. No, not 42 yet 64. BootROM's search-count setting is expressed in 64-page blocks. Meanwhile, kobs-ng uses an erase block as its stride: the Samsung NAND has 512k/4k = 128 pages per erase block. The OTP fuse controls how many 64-page blocks BootROM skips:

The reference-manual excerpt describes BOOT_SEARCH_COUNT as the number of 64-page blocks skipped when searching; its default value of 0 means four such blocks, or 256 pages. In the patched kobs-ng, the size of one search area is calculated in erase blocks. For the default BootROM setting, the two search-area sizes therefore need to agree:

4 × 64 pages = 2^search_exponent × (erase block size / page size)

On the EVK, --search_exponent=1 gives 2 × (512 KiB / 4 KiB) = 256 pages. On my 2 KiB-page custom board, the default exponent of 2 gives 4 × (128 KiB / 2 KiB) = 256 pages. This matches the search-area boundaries; the placement of copies within those areas and bad blocks also matter. I did not test changing the fuse.

So the solution was to pass the --search_exponent=1 argument to kobs-ng. linux-itb.sb is the same bootstream containing an ITB file that I used to boot from USB, see Booting via USB:

SPI Ethernet in U-Boot

The i.MX23 U-Boot branch eventually got an ENC28J60 driver and EVK support too. SPI Ethernet shares pins with the SD card, so U-Boot enables it when booted from USB or NAND, not SD. Connect the EVK's Ethernet port to the host and keep using the serial console for U-Boot.

USB Ethernet was already active here. The ENC28J60 had no valid MAC address, so I gave it one and selected it:

=> net list

Samsung NAND erase block size detection bugs

I ran mtdinfo -a and got a 512MB erase size for the Samsung K9LBG08U0D NAND flash. Even if technological advancement in microelectronics is happening rapidly, I would not expect 512MB. (Just looked up 🙄: up to 96MB erase block size for QLC NAND.) Searching the internet turned up a similar issue: https://archlinuxarm.org/forum/viewtopic.php?f=33&t=14511.

Every other NAND flash characteristic was printed as the data sheet suggested, most importantly page size = 4k and OOB size = 218 bytes.

Where could the bug be hiding? To answer this question we need to know, roughly, how the Linux NAND subsystem is organised: | Linux NAND subsystem | Source file(s) | | --- | --- | | Filesystem driver | SquashFS, UBI/UBIFS | | MTD driver | drivers/mtd/mtd*.c | | NAND base layer | drivers/mtd/nand/raw/nand_base.c and its consorts | | NAND SoC driver | drivers/mtd/nand/raw/gpmi-nand/gpmi_nand.c | | NAND chip driver | drivers/mtd/nand/raw/nand_samsung.c |

The NAND chip driver is responsible for identifying the chip, meaning the page size, OOB size and erase block size are determined by that driver. After spending a few hours reading nand_samsung.c, I finally spotted something interesting:

        /* Get blocksize */
        extid >>= 2;
        memorg->pages_per_eraseblock = (128 * 1024) <<
                           (((extid >> 1) & 0x04) |
                        (extid & 0x03)) /
                           memorg->pagesize;
        mtd->erasesize = (128 * 1024) <<
                 (((extid >> 1) & 0x04) | (extid & 0x03));

Those missing brackets around numerator before dividing by pagesize are sneaky! A very typical bug, though; I wonder how long it survived there. Anyway, after the numerator was put in brackets, see the patch, the erase size shows up correctly:

UBIFS and MLC NAND

Having fixed the wrong erase block size, I tried to create a UBIFS partition and immediately failed with ubi: refuse attaching mtd1 - MLC NAND is not supported. Well, MLC NAND is unsupported by UBIFS.

Searching the internet revealed great news from 2020: SLC NAND can be emulated in software! Interestingly, skimming through the U-Boot source code I found no sign of SLC emulation. I might have looked in the wrong place, though.

GPMI driver bugs

Even though there were many bit-flip errors, UBIFS could heal the partition by reading and rewriting its data. However, the NAND flash could not have been worn out. There must have been something wrong. What do you do when you don't know what to try next? Right, you 'consult' the internet. The closest I could find was this post: https://linux-mtd.infradead.narkive.com/fgiINLRg/bit-flip-detection-after-boot. Not so helpful, though, since it offered no solution or even a tip on how to narrow the issue down.

What do you do when searching for a bug in an unfamiliar codebase? The answer is: activate all log messages and increase the log level from debug to something more visible! That's what I did in gpmi-nand.c, and at some point No fingerprint found caught my eye. While reading gpmi-nand.c, I stumbled upon an iMX23-specific feature called NAND transcribing, which is required for the BCH hardware used for error correction. NAND transcribing means that bad block marks usually stored in the first OOB byte are transcribed (copied) into the first page bytes (at position 0). Once this is done, the "STMP" fingerprint is written at byte position 12 in the first NAND flash page to prevent transcribing again and corrupting data, which appears as bit-flips at the next boot. BTW, the "STMP" fingerprint is included in the header of a bootstream written by kobs-ng:

The first 4 bytes of the NCB block above are reserved for the "STMP" fingerprint.

The rest of the story is straightforward. The fingerprint had been written at byte position 22 - an offset by the length of the metadata. After crafting and applying this patch https://github.com/xaelsouth/buildroot/blob/feature/imx23/board/freescale/common/patches/linux/6.6.143/0012-gpmi-nand.patch to shift the fingerprint to its correct position, the bit flips were gone. Another ten-year-old bug mystery solved!

SPI Ethernet ENC28J60

Yeah, good ol' ENC28J60. I do wonder in how many projects, not just DIY ones, it has beaten into...

To support SPI Ethernet I used imx23-evk.dts and replaced eMMC with SPI: https://github.com/xaelsouth/buildroot/blob/feature/imx23/board/freescale/imx23evk/patches/linux/6.6.143/0003-spi-ethernet-enc28j60.patch.

DCP crypto

The reference manual says boot images are encrypted and include an authenticating hash; the image must be encrypted and authenticated with the appropriate key set before the BootROM can load and boot it.

This is why kobs-ng needs DCP crypto support when the device's OTP crypto key is set. The manual notes that the customer-programmed OTP AES key is never visible to software; DCP can use that key for AES operations. kobs-ng must use those operations to process the encrypted bootstream key/header material and its authentication data without reading the OTP key itself. Despite not having OTP crrypto key set, I wanted to make the DCP crypto hardware usable with kobs-ng. Again, you don't this if you use standard all-zeros OTP crypto key or pass the crypto key via command line.

Luckily, usbarmory provides required patches. I 'married' them to work with Linux kernel 6.6 I have been using:

  2. https://github.com/xaelsouth/buildroot/blob/feature/imx23/board/freescale/common/patches/linux/6.6.143/0018-dcp-to-support-otp-crypto-keys-2of2.patch.

TV-out

TV-out did not work in the initial Olinuxino test and did not seem to be the highest priority. But leaving yet another peripheral unsupported would have been too easy, wouldn't it? 😜 So, for the first time in my life, I asked AI to help with driver forward-porting and writing this chapter. The Buildroot branch now includes patches for composite output. The old Linux 2.6.31-era TV encoder support was forward-ported and adapted to the current DRM/KMS driver. The encoder register programming also refers to the i.MX23 reference manual and the older Freescale BSP tvenc driver.

The patches add a TV encoder DRM bridge and composite connector, along with the required clocks and device-tree connections for the Olinuxino and EVK. The LCDIF converts the framebuffer from RGB to YCbCr 4:2:2, generates an interlaced BT.656 stream and feeds it to the on-chip TV encoder. The driver provides PAL-B at 720x576 and NTSC-M at 720x480.

The output is selected at boot with the mxsfb.output kernel parameter: lcd, tv_pal or tv_ntsc. The Olinuxino configuration selects PAL by default; the EVK configuration selects the LCD by default. To change the default, edit the CONFIG_CMDLINE setting in the board's linux-tvenc.fragment and rebuild. The EVK selects either the LCD or TV output, not both at once.
